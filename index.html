Frequently asked

FCR provides faster confirmation by optimizing for user speed, while respected finality provides estimate economic security-alternative security considerations for different transaction thresholds.

What is the Fast Confirmation Rule? +
FCR provides faster confirmation by analyzing real-time attestation weight, allowing applications to consider blocks confirmed in ~13 seconds instead of waiting for full finality.
Does FCR require a hard fork? +
No. FCR is implemented entirely at the client level and requires no protocol changes or hard forks.
How fast is FCR compared to FFG finality? +
FCR provides confirmation in ~12-13 seconds (1-2 slots), compared to FFG finality which takes ~12-18 minutes (2 epochs).
What are the security tradeoffs? +
FCR relies on network synchrony and a 20-30% adversarial threshold, while FFG provides absolute finality with a 33% threshold. FCR is suitable for most everyday transactions.
What happens during network issues? +
Applications should monitor network conditions and fall back to FFG finality during periods of instability or for high-value transactions.
Which consensus clients support FCR? +
Support is being added to major clients including Lighthouse, Prysm, and Teku. Check the documentation for the latest compatibility.
How do I implement FCR? +
Enable the flag on your consensus client, query the new Beacon API endpoint, and update your confirmation logic to use FCR status alongside FFG.
Should I use FCR for all transactions? +
FCR is ideal for small to medium transactions. For large or high-value transactions, wait for full FFG finality.
